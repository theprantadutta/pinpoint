## 2. User-facing impact

**The purchase bug — what used to break.** `_SubscriptionScreenState.dispose()` called
`SubscriptionService.dispose()`, whose entire body cancelled the `purchaseStream` subscription.
The listener is process-lifetime and nothing re-subscribes (`initialize()` runs once from
HomeScreen behind a static guard). So the *first* time a user closed the paywall, the app stopped
listening to the store for the rest of the session. A buyer who opened the paywall, backed out,
reopened it and bought — or whose Play/StoreKit purchase resolved a moment after the sheet closed,
or came back as a deferred/pending payment — had their purchase **delivered to a dead listener**:
no backend verification, no entitlement, no `completePurchase`. They were charged and got nothing,
and on Play an uncompleted purchase auto-refunds after ~3 days, so the money went back too.

**What works now.** Exactly one listener per process, created once and never cancelled by UI.
A purchase that arrives after the paywall is closed (or closed and reopened) is still received,
verified and completed. This is pinned by a widget test that mounts the *real* `SubscriptionScreen`,
opens/closes/reopens/closes it, then delivers the purchase — plus a canary test replaying the old
teardown that asserts the opposite outcome (listener dead, zero events, nothing completed).

`initialize()` is also now idempotent and concurrency-safe, so a second call cannot spawn a second
listener (which would double-verify and double-complete) or trigger a duplicate restore storm.

**Cancellations are now handled.** `PurchaseStatus.canceled` had no branch at all; it fell through
silently. It is now handled explicitly (and `completePurchase` is called only when
`pendingCompletePurchase` is true — on iOS SK1 this finishes a transaction that was previously
left dangling; that is a genuine iOS behaviour change).

**Paywall honesty.** A buyer now sees 6 bullets that are all true and all enforced. Gone:
"Unlimited images & attachments" (the shipping editor has no attach UI at all), "Drawing notes"
(unreachable for every tier), "Encrypted note sharing" (the app's own menu item says SOON),
"Priority support" (no support channel in-app). "All accent colors & themes" became "All accent
colors" — themes and all 8 bundled fonts are free.

*Follow-up, same day:* **"Unlimited voice recording length" was restored** — but only after the cap
was made real. It had been cut because nothing enforced it: the live recorder's timer only counted
up, and the widget that checked `getMaxVoiceRecordingDuration()` (`record_type_content.dart`) has no
importers. The recording timer in `create_note_screen_v2.dart` now stops a free user at
`maxVoiceRecordingDurationForFree` (2 min), keeps the audio recorded so far, and shows
`PremiumGateDialog.showVoiceRecordingLimit`. The per-note **attachment** cap was NOT restored — there
is no attachment picker in the shipping editor, so there is nothing to gate.

**Onboarding copy** no longer promises drawings (slide 1) or tags (slide 2); there is no tag UI.

**Device logs** no longer contain a purchase-token prefix in release builds.

### Removed from the wire (no longer emitted at all)

| Old event | Old params | What it actually measured |
|---|---|---|
| `purchase_initiated` | `product_id` | paywall button tap |
| `purchase_completed` | `product_id` | **billing-sheet launch**, not a purchase |
| `purchase_failed` | `product_id`, `error` (free text, `e.toString()`) | two unrelated branches |

`trackPurchaseInitiated` / `trackPurchaseCompleted` / `trackPurchaseFailed` are gone from the
interface and all three implementations. Verified: zero hits in `lib/`; the only remaining
references are guard tests asserting their absence.

### New events

| Event | Params | Emitted by |
|---|---|---|
| `checkout_started` | `product_id` | `subscription_screen.dart` `_purchaseSubscription()` |
| `checkout_launch_succeeded` | `product_id` | `SubscriptionService.purchase()` |
| `checkout_launch_failed` | `product_id`, `reason` | `SubscriptionService.purchase()` |
| `checkout_pending` | `product_id` | `_onPurchaseUpdate` |
| `checkout_cancelled` | `product_id` | `_onPurchaseUpdate` |
| `checkout_error` | `product_id`, `reason` | `_onPurchaseUpdate` |
| `store_purchase_confirmed` | `product_id`, `source` | `_onPurchaseUpdate` |
| **`purchase_verified`** | `product_id`, `platform`, `source` | `_handleSuccessfulPurchase` (confirmed only); `SubscriptionManager` on a successful retry |
| `purchase_provisionally_granted` | `product_id`, `platform`, `reason` | `_handleSuccessfulPurchase` |
| `verification_failed` | `product_id`, `reason` | `_handleSuccessfulPurchase` |
| `search_performed` | `query_length_bucket` (was `query`) | `notes_screen.dart` |

Unchanged: `subscription_screen_viewed`, `restore_purchase_initiated`.

Closed value sets: `source` ∈ {`purchase`, `restore`}; `platform` ∈ {`android`, `ios`};
`reason` on `checkout_launch_failed` ∈ {`store_unavailable`, `product_not_found`, `launch_rejected`,
lower-cased `PlatformException.code` clamped to 100 chars, `unknown`}; on `checkout_error` the
sanitized `IAPError.code` or `unknown`; on `verification_failed` ∈ {`verification_rejected`,
`no_purchase_token`}. All parameter values are `String`.

### THE conversion event is `purchase_verified`

It is emitted only from `_handleSuccessfulPurchase` inside the `if (verified)` branch, which is only
reachable from the purchase stream — never from a button tap.

### Warning — historical data is not comparable

- **`purchase_completed` and `purchase_verified` measure different things.** The old event fired when
  `buyNonConsumable` merely *launched* the store sheet: before `PurchaseStatus.purchased`, before
  backend verification. It counted sheet openings, including every cancellation and every failure.
  `purchase_verified` counts verified purchases. **The new number will be substantially lower.**
  Do not chart them on one series, do not compute period-over-period growth across the release
  boundary, and do not read the drop as a regression — it is the bug being fixed.
- **Any saved GA4/Firebase/BigQuery funnel, audience, conversion-event registration, or Google Ads
  conversion import keyed on `purchase_initiated` / `purchase_completed` / `purchase_failed` will go
  flat from the first release that ships this.** They must be re-pointed at `checkout_started` /
  `purchase_verified` / `checkout_launch_failed`.
- **`search_performed` changed shape.** Any report on `search_performed.query` breaks; the parameter
  no longer exists. Event volume is unchanged (still on the 280 ms debounce, so one typed query still
  emits several events) — only the content is gone.
- **`purchase_verified` counts confirmed sales only.** *(Resolved in a follow-up on the same day —
  it is no longer optimistic.)* `SubscriptionManager.verifyPurchase()` now returns a
  `PurchaseVerificationResult` (`confirmed` / `provisional` / `failed`) instead of a bare `bool`, so
  the three outcomes are separate events:
  | Outcome | Event | Counts as a sale? |
  |---|---|---|
  | Backend confirmed | `purchase_verified` | **Yes** |
  | Store charged, backend rejected or unreachable | `purchase_provisionally_granted` (`product_id`, `platform`, `reason` ∈ {`backend_rejected`, `backend_unreachable`}) | No — an entitlement |
  | Could not verify at all | `verification_failed` (`reason` ∈ {`no_device_id`, `no_purchase_token`, `verification_rejected`}) | No |

  When the background retry later confirms a provisional purchase, `SubscriptionManager` emits
  `purchase_verified` with **`source: 'retry'`** — so `source` is now a closed set of
  {`purchase`, `restore`, `retry`}. Without that the funnel would have swung from over-counting to
  *under*-counting, because a purchase that went out provisionally would never produce a conversion
  event at all. A persistent gap between `purchase_provisionally_granted` and the matching
  `source: 'retry'` confirmation means the verification endpoint is failing and paying users are
  running on trust — worth an alert.

## 5. Privacy trade-off, documented

### What search telemetry collects now

`search_performed` carries exactly one parameter, `query_length_bucket`, whose value is one of four
literals: `1-3`, `4-10`, `11-25`, `26+`. It is derived from `query.trim().runes.length` in
`notes_screen.dart`. **No search text, no prefix, no truncation, no hash.** Verified:
`grep -rn "'query'" lib/` returns nothing; all four analytics files declare `int queryLength`.

The residual disclosure is behavioural, not content: Google can see that a search happened and roughly
how long the string was. Because the emit is still on the 280 ms debounce, one typed query emits
several events — several length buckets instead of several prefixes of the user's text. Event volume
is unchanged.

### Why hashing was rejected

A hash of a short search query is trivially reversible by dictionary attack, and a hash is still a
deterministic function of note content — it would let anyone holding the events link identical
searches across sessions and users. On an E2EE note app, a search term *is* note content. A coarse
length bucket is not derived from any specific content and cannot be inverted.

### Deliberately left unchanged — input to a follow-up privacy pass

All of the following were identified and **not** touched, to keep this task in scope. All were
re-verified as still present:

1. **`lib\screens\sync_screen.dart:71` and `:89`** — `trackSyncFailed(error: result.message)` and
   `trackSyncFailed(error: e.toString())` ship raw error text to the Firebase `error` parameter.
   `result.message` is built upstream from `e.toString()` in `api_sync_service.dart` (241/333/553) and
   `folder_sync_service.dart` (54/103/192). Dio errors stringify to include the request URI and can
   carry the server response body; the folder-sync messages carry **user-authored folder names**.
   *Same leak class as the search query and arguably wider. Highest-priority follow-up.*
2. **`lib\services\crash_breadcrumbs.dart:83`** — `popupMenuClosed(String id, {Object? selected})`
   writes free-text `selected` to `FirebaseCrashlytics.log()`. All current call sites pass code
   constants, so this is latent, not actual. `setKey`/`setCustomKey` (line 57) is equally open.
3. **`lib\services\api_service.dart` 1023 / 1047 / 1101 / 1112** — exception messages interpolate
   server-supplied `response.data['message']` prose and `userId/filename` server paths. Uncaught, these
   are reported verbatim by the Crashlytics global handlers in `main.dart`.
4. **`lib\services\encryption_service.dart:246`** — `throw Exception('Failed to decrypt data: $e')`,
   same Crashlytics exposure.
5. **`setUserId` / `setUserIdentifier`** with the account UID (`auth_screen.dart` 593/744,
   `backend_auth_service.dart:133`) — deliberate and correctly nulled on logout, but it *is* a user
   identifier and must be declared in Data safety.
6. **`AnalyticsFacade._eventQueue` is unbounded** and is drained only by `onFirebaseReady()`, called
   inside the `try` of `main.dart`'s `_initializeFirebaseInBackground()`. If the preceding `await`
   throws, the queue grows for the whole session, each entry retaining its captured argument strings.
7. **Pre-existing `bool`-parameter marshalling defect** in `firebase_analytics_client.dart`
   (`trackBiometricToggled`, `trackHighContrastToggled`, `trackNotificationPermissionResult`) — the
   SDK asserts `String || num`, and asserts are stripped in release. Not a leak, but the same file.
   All *new* events use `String` only.
